Designing a safe AI refund agent

A customer asks your AI for a $500 refund. The AI can say yes, and still never touch the money. This blueprint shows how: the architecture, the request flow, safe retries, failure cases, and how to test it.

3 · The timeout: a blind retry vs a safe one

A timeout doesn't mean the refund failed. It means you don't know yet. Play both versions side by side.

The rule: commit the operation, its idempotency key and the exact provider request before the first call. Retry only with that same key and the same stored request, with backoff and a retry budget. Provider deduplication only lasts for its documented window, so outside it, or whenever you can't confirm the outcome, reconcile first. Never send a "fresh" request while the original outcome is unknown.

③ Refund service → payment provider (with the idempotency key)

// 1. One transaction, COMMITTED before any provider call:
//    consume the approval, reserve the amount, store the exact request
BEGIN;
  UPDATE approvals SET consumed_at = now()
   WHERE id = 'apr_7F3A' AND consumed_at IS NULL AND expires_at > now();
  INSERT refund_ledger (operation_id, approval_id, idempotency_key,
                        amount, request, submission, provider_status)
  VALUES ('op_7F3A', 'apr_7F3A', 'refund:apr_7F3A',
          50000, '{...exact body below...}', 'PREPARED', NULL);
  INSERT outbox (operation_id) VALUES ('op_7F3A');
COMMIT;

④ Timeout → retry or reconcile

// Timeout: outcome unknown. Conditional, so it never overwrites
// a result a webhook already recorded
UPDATE refund_ledger SET submission = 'UNKNOWN', version = version + 1
 WHERE operation_id = 'op_7F3A' AND submission = 'SENT' AND version = 3;

// Safe retry (inside the provider's deduplication window):
// same key, the SAME stored request body
POST /v1/refunds
Idempotency-Key: refund:apr_7F3A        → replays the first result
                                          (which can itself be an error)

// Or reconcile: list refunds for the payment, match amount, currency
// and metadata.approval_id; or wait for a signature-verified webhook
GET /v1/refunds?payment=pay_9K2          → re_3QX, status "pending"
webhook: refund.updated { "id": "re_3QX", "status": "succeeded",
                          "metadata": { "approval_id": "apr_7F3A" } }

UPDATE refund_ledger SET submission = 'RESOLVED',
       provider_status = 'succeeded', provider_refund_id = 're_3QX'
 WHERE operation_id = 'op_7F3A' AND provider_status IS DISTINCT FROM 'succeeded';
// Nothing found? Keep it UNKNOWN and escalate. An empty lookup
// doesn't prove an in-flight request won't still land.

7 · Ten design rules

  1. The agent holds no payment credentials. It has no tool that can move money, so even a manipulated agent can't execute.
  2. Agent tools are read-only and scoped to the signed-in customer. Identity comes from the session, never from chat text.
  3. Check ownership on every object. The order must belong to the authenticated customer (object-level authorization).
  4. Proposals are structured, not prose. Schema-validated fields plus evidence references.
  5. The policy engine fetches its own facts. It re-reads the order and delivery status instead of trusting the agent's summary. Claims it can't verify, like damage, need evidence or a human.
  6. Rules are deterministic and versioned. Same facts, same policy version, same decision. Every decision records the version, the time and the facts it used.
  7. Enforcement lives in the executor. The refund service only starts an operation from an authentic, unexpired, unconsumed approval bound to that customer, payment, amount and currency, and reserves the amount atomically.
  8. Commit before you call. The operation, its idempotency key and the exact request are committed before the first provider call, so every retry resumes the same operation.
  9. Unknown outcomes get resolved, not guessed. Retry only with the same key inside the provider's window; otherwise reconcile with lookups and signature-verified webhooks, and escalate anything still unresolved.
  10. Humans handle exceptions and high value. Reviewers are authorised and their overrides logged. Trace and evaluate everything, with direct identifiers removed.
